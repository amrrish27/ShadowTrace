Executive Summary & Abstract

Abstract

Modern application engineering is defined by agile microservices, decentralized engineering teams, and Single-Page Applications (SPAs) communicating over hundreds of distributed RESTful and GraphQL endpoints. While this distributed architecture accelerates feature delivery, it creates a severe organizational blindspot: uncontrolled API sprawl. Over time, continuous deployment cycles leave behind uncataloged Shadow APIs (developer test routes or staging interfaces), deprecated but actively reachable Zombie APIs (unretired v1 routes left exposed when v2 launched), and orphaned endpoints that completely bypass central security controls, rate limiters, and Web Application Firewalls (WAFs). This critical exposure vector is formalized as API9:2023 (Improper Inventory Management) in the OWASP API Security Top 10 and represents one of the fastest-growing attack surfaces exploited in modern enterprise data breaches.

ShadowTrace is an automated, production-grade API attack surface discovery, security auditing, and inventory governance platform engineered during the HackHalt Cybersecurity Engineering Internship. Designed from the ground up to solve the enterprise visibility gap, ShadowTrace integrates multi-source passive bundle scraping (including JavaScript abstract syntax tree parsing and source map reconstruction), non-destructive active heuristic probing, dynamic regex parameter tokenization, OpenAPI differential baseline reconciliation, and mathematical risk prioritization into a unified, high-performance platform. By combining safe, idempotent validation with strict Server-Side Request Forgery (SSRF) boundary controls, ShadowTrace empowers security teams to identify, validate, and remediate unmanaged API attack surfaces without risking operational disruption or data corruption.

The API9:2023 Threat Paradigm & Problem Context

Traditional Dynamic Application Security Testing (DAST) scanners and network vulnerability analyzers were constructed around static, multi-page application paradigms. When deployed against modern distributed architectures, these legacy tools exhibit severe structural failures:

  • Inability to Reconstruct Client Route Registries: Single-Page Applications (React, Vue, Angular) compile hundreds of API routes inside minified JavaScript bundles and asynchronous chunks. Legacy crawlers that only parse server-rendered HTML tags miss up to 85% of client-invoked API endpoints.
  • Route Explosion from Dynamic URL Parameters: In RESTful architectures, identifiers are embedded directly into URL paths (e.g., /api/users/9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d/orders/84729). Without intelligent path templating, naive crawlers treat every unique ID as a distinct endpoint, causing combinatorial explosion, scan timeouts, and massive report redundancy.
  • Single-Page Application Soft-404 False Positives: Modern SPA client-side routers respond to arbitrary, non-existent paths with HTTP 200 OK by serving the root HTML bundle (index.html). Traditional scanners falsely catalog thousands of phantom routes as live APIs, overwhelming security analysts with false-positive alerts.
  • Blindness to Schema Drift and Version Deprecation: Development teams rarely synchronize production routing changes with static OpenAPI or Swagger documentation. Undocumented routes, deprecated parameters, and zombie API versions persist indefinitely without security oversight.

CHAPTER 1

The Modern API Threat Landscape & Problem Definition

1.1 The Proliferation of Microservices and Single-Page Architectures

Over the past decade, enterprise software engineering has undergone a profound architectural migration from monolithic codebases to distributed microservice ecosystems and decoupled Single-Page Applications (SPAs). While this architectural paradigm enables continuous deployment and independent team velocity, it distributes application business logic across hundreds—often thousands—of distinct RESTful, RPC, and GraphQL network endpoints.

In contemporary cloud environments (AWS, GCP, Azure, and Kubernetes clusters), microservices communicate internally across private service meshes and externally through API Gateways and reverse proxies. However, as organizational development cadence accelerates, engineering synchronization routinely breaks down. Teams frequently release rapid hotfixes, spin up staging instances, create temporary webhook handlers, or refactor legacy controllers without updating central documentation or revoking legacy routing entries.

The resultant organizational state is termed API Sprawl. Security operations centers (SOCs) and AppSec teams find themselves responsible for defending attack surfaces whose exact perimeter, inventory, and exposed parameters are completely unknown. You cannot protect what you cannot see, and modern threat actors explicitly target forgotten, undocumented routes that exist outside the visibility of Web Application Firewalls (WAFs) and centralized authentication gateways.

1.3 OWASP API Security Top 10 (2023) Focus: API9:2023

The Open Worldwide Application Security Project (OWASP) recognized unmanaged APIs as a top-tier vulnerability category, codifying it as API9:2023: Improper Inventory Management in the official OWASP API Security Top 10 standard. OWASP explicitly warns:

OWASP API9:2023 Definition: APIs tend to expose more endpoints than traditional web applications, making proper and updated documentation critical. Proper inventory of hosts and deployed API versions plays an important role in mitigating issues such as deprecated API versions and exposed debug endpoints. Lack of asset management allows attackers to exploit unpatched legacy endpoints that still possess access to production databases.

Modern threat actors specifically harvest client-side JavaScript bundles to locate old API routes. Because development teams assume legacy routes are forgotten, they rarely patch vulnerabilities in older code paths. Consequently, a Zombie v1 endpoint often provides an attacker with direct SQL injection or Broken Object-Level Authorization (BOLA) directly into current production databases, completely bypassing the robust security controls implemented in modern v2 endpoints.

2.3 The Non-Destructive Safe Probing Mandate & RFC 9110 Idempotency

A primary failure mode of commercial vulnerability scanners is operational disruption. Heavy scanners often inject fuzzing payloads or mutate server records by issuing unconstrained POST, PUT, or DELETE requests. In production environments, this can corrupt databases, trigger false financial transactions, or trigger denial-of-service (DoS) conditions.

ShadowTrace enforces a strict Non-Destructive Safe Probing Mandate based on the safe method definitions codified in RFC 9110 (HTTP Semantics). Section 9.2.1 of RFC 9110 establishes:

RFC 9110 Section 9.2.1 Safe Methods: Request methods are considered 'safe' if their defined semantics are essentially read-only; that is, the client does not request, and does not expect, any state change on the origin server as a result of applying such a method. The methods GET, HEAD, OPTIONS, and TRACE are defined as safe.

ShadowTrace's discovery and active verification engines are strictly prohibited from generating mutating HTTP requests. Active probes verify route existence, header configurations, authentication challenges, and CORS policies exclusively through safe GET, HEAD, and OPTIONS requests. This architectural constraint allows organizations to run continuous ShadowTrace audits against live production systems without risk of database corruption or business disruption.

2.4 Attestation Logging & Cryptographic Audit Trail Architecture

Operators must attest to having lawful authorization to test the targeted domain.

3.2 The 6-Stage Autonomous Discovery & Auditing Pipeline

The core intelligence of ShadowTrace resides in its deterministic 6-stage discovery and auditing pipeline. Each scan job progresses sequentially through these six distinct phases, emitting progress events to connected clients via Server-Sent Events (SSE):

  • Stage 1: Pre-Flight Validation & SSRF Guardrail Verification: Normalizes the target URL, extracts the canonical host, executes DNS pre-resolution, and tests all candidate IP addresses against zero-trust private network blacklists. If an IP resolves to private subnets or cloud metadata, the scan is rejected immediately.
  • Stage 2: Passive Spidering & Asset Harvesting: Initiates breadth-first HTTP crawling of the target domain. Parses HTML documents to harvest script tags, stylesheets, client manifests, and navigational links up to configured crawl depth.
  • Stage 3: JavaScript Lexical Parsing & Source Map Reconstruction: Downloads external and inline script bundles. Applies lexical tokenization and AST regex extractors to discover API calls (fetch, axios, ajax). Probes for corresponding .map files to reconstruct original developer source files.
  • Stage 4: Dynamic Parameter Tokenization & Route Normalization: Passes all discovered URL strings through the path templating engine. Concrete resource identifiers (UUIDs, sequential numbers, hashes, slugs) are tokenized into parameterized schemas to prevent route explosion.
  • Stage 5: OpenAPI Baseline Differential Reconciliation: Compares normalized routes against uploaded OpenAPI / Swagger baseline documentation. Flags undocumented routes as Shadow APIs, unretired old versions as Zombie APIs, and missing controllers as Orphaned APIs.
  • Stage 6: Safe Heuristic Validation & Monotonic Risk Scoring: Performs multi-sample soft-404 baseline calibration, validates live endpoint status codes via safe GET/HEAD requests, evaluates 17 security rules, and computes bounded mathematical risk scores.

3.3 Concurrency, Async Scheduling & Queue Backpressure Management

To ensure high scanning throughput without overwhelming target infrastructure or exceeding system memory limits, the discovery engine is constructed entirely upon Python's native asyncio event loop. Key concurrency features include:

  • Semaphore-Bounded Worker Pools: Network requests are throttled using asyncio.Semaphore to limit concurrent connections per target host (default: 10 concurrent requests). This prevents denial-of-service conditions on target servers.
  • Async Connection Pooling via HTTPX: Connection reuse, HTTP/2 multiplexing, and keep-alive socket pools are managed via httpx.AsyncClient, minimizing TCP handshake and TLS negotiation overhead.
  • Streaming Event Pipeline: Scan events, discovered endpoints, and security findings are queued in memory and flushed asynchronously to the persistence layer and SSE broadcast channels, eliminating I/O bottlenecks.

3.4 SQLite Write-Ahead Logging (WAL) Mode Transactional Model

While standard SQLite locks the entire database file during write transactions (causing database is locked errors under concurrent web and scanning workloads), ShadowTrace configures SQLite in Write-Ahead Logging (WAL) mode.

In WAL mode, readers do not block writers, and writers do not block readers. Changes are written to a separate -wal journal file and periodically checkpointed back to the primary database file. The initialization sequence executes the following performance pragmas: 

PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA busy_timeout=5000;
PRAGMA cache_size=-64000; -- 64MB memory cache
PRAGMA foreign_keys=ON;

This configuration allows the background scanner to write continuous endpoint discoveries and finding records at high velocity while the web server concurrently serves dashboard queries and SSE streams to operators with zero locking latency.

CHAPTER 4

Discovery Engine & Passive Crawling Subsystem

4.1 Breadth-First Web Spidering & Asset Harvesting

The discovery pipeline begins with a deterministic breadth-first web spidering engine designed to traverse the target domain's public web surface without triggering defensive bot blocks or exceeding resource constraints. The crawler initiates from the root target URL and extracts links and embedded assets up to a configurable depth limit (default: 3 levels).

To ensure focused and ethical testing, the spider enforces strict boundary constraints:

  • Same-Origin & In-Scope Domain Boundary: The spider resolves candidate URLs and rejects any outbound link pointing outside the target apex domain or authorized subdomains.
  • Media & Binary Exclusion Filters: High-bandwidth binary assets (images, videos, audio, PDF documents, fonts, compressed archives) are filtered out via file extension matching and pre-flight MIME type checks, conserving network bandwidth.
  • Visited Set Deduplication: URLs are canonicalized (stripping tracking fragments, UTM query parameters, and normalizing trailing slashes) and checked against an in-memory SHA-256 hash set to prevent circular link loops.

4.2 JavaScript Lexical Parsing & Abstract Syntax Tree Tokenization

Modern Single-Page Applications (SPAs) built with React, Vue, Angular, Svelte, or Next.js do not expose application navigation in traditional HTML anchor tags (<a href="...">). Instead, routes are declared inside client-side router configurations (React Router, Vue Router) and invoked via dynamic HTTP clients (Fetch API, Axios, jQuery AJAX).

To uncover these hidden endpoints, ShadowTrace implements a dedicated JavaScript Lexical Tokenizer and Abstract Syntax Tree (AST) analyzer. As script assets are harvested, the parser executes a series of optimized multi-stage regular expression extractors: 

// Comprehensive Lexical Extraction Patterns for Client-Side Script Bundles
const FETCH_AXIOS_REGEX = /(?:fetch|axios(?:\.get|\.post|\.put|\.delete|\.patch)?)\s*\(\s*['"`]([a-zA-Z0-9_\-\.\/:\$]+)['"`]/gi;
const API_PREFIX_REGEX = /['"`](\/(?:api|v[0-9]+|rest|graphql|internal|auth|v1|v2|v3)\/[a-zA-Z0-9_\-\.\/]+)['"`]/gi;
const ENDPOINT_STRING_REGEX = /['"`](https?:\/\/[a-zA-Z0-9_\-\.:]+\/(?:api|v[0-9]+)\/[a-zA-Z0-9_\-\.\/]+)['"`]/gi;

The lexical parser extracts string literals matching standard API path conventions, template strings (e.g., `/api/users/${userId}/profile`), and relative path constants. Discovered candidates are normalized and queued for parameter templating and verification.

4.3 Source Map Reconstruction & Developer Code Recovery

One of ShadowTrace's most potent offensive and defensive capabilities is its automated Source Map (.map) Reconstruction Engine. When developers build modern frontend applications using Vite, Webpack, esbuild, or Rollup, production source code is typically minified, obfuscated, and bundled into monolithic JavaScript files.

However, development and DevOps teams frequently neglect to disable source map generation or inadvertently deploy .js.map files to public production servers. Source maps contain a complete, unminified snapshot of the original developer repository, including original file paths, TypeScript source files, unredacted comments, private backend route definitions, and internal API URLs.

Safe Heuristic Validation & Soft-404 Mitigation Engine

6.1 The Single-Page Application (SPA) Catch-All Routing Challenge

One of the most pervasive failure modes in automated API security scanning is the Single-Page Application (SPA) Soft-404 problem. In standard server-rendered architectures (e.g., Apache, Nginx serving PHP or Java), requesting a non-existent URL (such as /api/non-existent-endpoint-xyz) causes the web server to emit a definitive HTTP 404 Not Found status code.

However, modern web architectures deploy Single-Page Applications behind reverse proxies configured with client-side catch-all routing rules (e.g., try_files $uri $uri/ /index.html;). Under this configuration, when a client requests any arbitrary path, the server responds with HTTP 200 OK and serves the root HTML bundle (index.html), allowing the client-side JavaScript router (Vue Router, React Router) to handle page rendering.

To an automated scanner lacking soft-404 compensation, every single probed path appears to be a valid, live API endpoint returning HTTP 200 OK! The scanner mistakenly flags hundreds of phantom endpoints, generating massive report noise and destroying analyst trust in the tool.

6.2 Multi-Sample Baseline Calibration & Entropy Analysis

ShadowTrace eliminates soft-404 false positives through a sophisticated Multi-Sample Baseline Calibration Subsystem. Prior to executing active route validation, the engine issues a sequence of randomized, guaranteed-non-existent probes to establish the target host's fallback behavior:

  1. Random Token Path Probing: Generates three cryptographic random paths unlikely to exist on any system (e.g., /__shadowtrace_calib_8f3a9d1c/).
  2. Response Signature Profiling: Captures the HTTP status code, response headers, Content-Type, body byte length, and raw HTML/text payload for each calibration probe.
  3. Shannon Entropy Calculation: Computes the Shannon entropy of the response body to measure information density: 
      H(X) = - SUM [ P(x_i) * log2(P(x_i)) ]
    HTML fallback pages exhibit characteristic entropy signatures distinct from structured JSON API payloads.

6.3 Algorithmic Soft-404 Differentiator & False-Positive Elimination

During active validation of discovered candidate routes, every response is evaluated against the established calibration baseline using a multi-factor comparison algorithm:

Comparison Factor Evaluation Criteria Classification Decision
Content-Type Mismatch Candidate path claimed to be API, but server returned text/html matching root SPA page. Soft-404 (Catch-All): Flagged as client router fallback; suppressed from API findings.
Body Length Variance Response length within ±2% of calibration baseline byte length. Soft-404 (Catch-All): High probability of static HTML template fallback.
DOM Structure Similarity Levenshtein text distance or HTML tag sequence matching baseline with > 92% similarity. Soft-404 (Catch-All): Confirmed SPA fallback page.
JSON Structured Payload Response Content-Type is application/json with valid parseable JSON body. Genuine API Endpoint: Validated as live backend API service.
Definitive 404 / 405 Server returns explicit HTTP 404 Not Found or 405 Method Not Allowed. Genuine HTTP Route: Categorized as inactive or method-restricted route.

6.4 Non-Destructive Active Verification Protocol & Response Classification

Once candidate routes have been cleared of soft-404 catch-all interference, ShadowTrace executes its Non-Destructive Active Verification Protocol. The validator probes each canonical endpoint using safe, read-only HTTP methods:

  • Safe Method Probing (GET / HEAD): Emits a non-destructive GET request with standardized security evaluation headers (Accept: application/json, X-Scanner: ShadowTrace-Audit).
  • HTTP Options Exploration (OPTIONS): Issues an OPTIONS request to inspect the Allow and Access-Control-Allow-Methods response headers, cataloging supported backend HTTP verbs without invoking them.
  • Status Code Categorization:
    • 200–299 (Success): Endpoint is live, active, and accessible.
    • 401 Unauthorized / 403 Forbidden: Endpoint exists and enforces authentication/authorization barriers.
    • 405 Method Not Allowed: Endpoint exists but restricts GET; records supported methods from headers.
    • 500 Internal Server Error: Endpoint exists but encountered an unhandled exception (potential vulnerability).

8.1 Mathematical Risk Formula & Variable Definitions

A persistent failure of commercial vulnerability management platforms is arbitrary, opaque risk scoring. Commercial tools frequently assign arbitrary 1–10 scores based on subjective proprietary algorithms, creating inconsistent prioritization across different audit runs.

ShadowTrace introduces a deterministic, formal Mathematical Risk Scoring Model. The risk score for each identified finding is bounded strictly between 0 and 100 and calculated as a function of four primary variables:

The ShadowTrace Formal Risk Formula:
RiskScore = min(100, round( S_base * C_factor * E_multiplier + V_penalty ))

The mathematical parameters are defined as follows:

  • Base Severity Score ($S_{base}$): The intrinsic theoretical severity of the vulnerability class based on CVSS v3.1 impact:
    • Critical (ST-001, ST-002): $S_{base} = 90.0$
    • High (ST-003, ST-005, ST-010, ST-013): $S_{base} = 70.0$
    • Medium (ST-004, ST-006, ST-007, ST-009, ST-011, ST-015): $S_{base} = 45.0$
    • Low (ST-008, ST-012, ST-014, ST-016): $S_{base} = 20.0$
    • Informational (ST-017): $S_{base} = 5.0$
  • Confidence Factor ($C_{factor} \in [0.5, 1.0]$): The empirical reliability of the discovery method:
    • $C = 1.0$: Verified via direct runtime HTTP response with status code 200 and valid JSON body.
    • $C = 0.85$: Extracted via unminified source map reconstruction with confirmed route syntax.
    • $C = 0.70$: Discovered via client script regex matching; unconfirmed active status.
    • $C = 0.50$: Inferred via soft-404 heuristic or ambiguous static string literal.
  • Exposure Multiplier ($E_{multiplier} \in [0.8, 1.2]$): The environmental accessibility of the endpoint:
    • $E = 1.2$: Public apex domain accessible without authentication or IP restrictions.
    • $E = 1.0$: Subdomain or internal route requiring standard user session credentials.
    • $E = 0.8$: Internal staging or administrative host protected by network access controls.
  • Verified Exploitability Penalty ($V_{penalty} \in \{0, 10\}$):
    • $V = +10$: If the active verification probe confirmed that sensitive data (PII, credentials, debug objects) was directly returned in the response payload.
    • $V = 0$: Standard configuration or route observation without immediate data leakage.

8.2 Formal Proof of Monotonicity & Bounded Range [0, 100]

To ensure that security teams can trust the automated ranking, the scoring function satisfies a crucial mathematical property: Monotonic Severity Ordering. A finding with higher base severity must always outrank a finding of lower base severity under equivalent confidence and exposure parameters.

Proof Sketch:
Let $A$ and $B$ be two findings such that $S_{base}(A) > S_{base}(B)$. For fixed confidence $C$ and exposure $E$: 

RiskScore(A) - RiskScore(B) = (S_base(A) - S_base(B)) * C * E + (V(A) - V(B))

Since $C \ge 0.5$ and $E \ge 0.8$, the product $C imes E \ge 0.40$. Across our calibrated severity steps:

  • Critical vs High: $\Delta S_{base} = 90 - 70 = 20$. Minimum score delta: $20 imes 0.4 = 8.0$.
  • High vs Medium: $\Delta S_{base} = 70 - 45 = 25$. Minimum score delta: $25 imes 0.4 = 10.0$.
  • Medium vs Low: $\Delta S_{base} = 45 - 20 = 25$. Minimum score delta: $25 imes 0.4 = 10.0$.
  • Low vs Info: $\Delta S_{base} = 20 - 5 = 15$. Minimum score delta: $15 imes 0.4 = 6.0$.

Because the maximum negative exploitability penalty offset $(V_B - V_A)$ cannot exceed 10 under equal conditions, the calibrated boundary tiers guarantee that high-severity findings reliably outrank lower-severity findings, preventing misallocated remediation effort.

9.1 The SSRF Threat Vector in Automated Security Tools

Automated vulnerability scanners and crawling tools are uniquely attractive targets for Server-Side Request Forgery (SSRF) attacks. Because a scanner accepts user-supplied URLs and issues outbound HTTP requests on behalf of the operator, an attacker with access to the tool can attempt to input malicious URLs pointing to internal private infrastructure: 

http://127.0.0.1:8000/admin/
http://10.0.0.15/internal-api/keys
http://169.254.169.254/latest/meta-data/iam/security-credentials/
http://[::1]:5432/

If the scanning engine blindly issues requests to these addresses, it acts as a weaponized internal proxy. An attacker can use the scanner to steal cloud instance credentials from the AWS metadata service, interact with internal Redis or PostgreSQL databases, or access unauthenticated microservices inside a private VPC.

9.2 Zero-Trust IP Validation Engine & RFC Blacklist Mapping

9.3 Anti-DNS-Rebinding Socket Pinning Architecture

A common vulnerability in naive SSRF defenses is the Time-of-Check to Time-of-Use (TOCTOU) DNS Rebinding attack. In this attack:

  1. An attacker configures a domain name (e.g., rebind.attacker.com) with a very low DNS Time-To-Live (TTL = 0 seconds).
  2. When ShadowTrace performs pre-flight validation, the domain resolves to a benign public IP (e.g., 1.1.1.1). The pre-flight check passes.
  3. Millisecond later, when the HTTP client actually initiates the connection, the attacker's DNS server answers with 169.254.169.254 or 127.0.0.1! The HTTP client connects directly to the private target, bypassing the pre-flight check.

To eliminate DNS rebinding entirely, ShadowTrace employs Socket-Level IP Pinning. The engine performs explicit DNS resolution up front, validates the IP address, and establishes the TCP socket directly to the validated IP address, passing the original domain name exclusively in the HTTP Host header and TLS Server Name Indication (SNI) extension. This eliminates any secondary DNS lookup, guaranteeing that the IP verified during pre-flight is the exact IP connected to at the socket level.

15.1 Technical Challenges Overcome & Internship Reflections

Engineering ShadowTrace during the HackHalt Cybersecurity Research Internship provided profound practical exposure to the intersection of offensive security research, distributed systems architecture, and robust full-stack software development. Several formidable engineering challenges were successfully solved:

  • Solving Asynchronous SQLite Concurrency: In high-throughput async pipelines, standard SQLite configurations frequently throw sqlite3.OperationalError: database is locked. By implementing Write-Ahead Logging (WAL) mode, tuning connection pool timeouts, and batching write operations through asynchronous queues, database locking was completely eliminated.

Developing the multi-sample Shannon entropy and body variance engine eliminated false positives without degrading scan speed.
